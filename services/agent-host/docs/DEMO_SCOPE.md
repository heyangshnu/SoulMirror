# fate-and-fortune Demo Scope

## 1. Demo 目的

第一版 demo 的目的不是做完整产品，也不是做真实排盘或报告生成。

它只验证一件事：

```text
五轴人物档案是否能清晰表达一个人的发展路径。
```

也就是：

```text
Person Dashboard
├─ 五轴总览
├─ 命盘时间骨架
├─ 执行路径
├─ 环境变化
├─ 关系网络
└─ 资源变化
```

## 2. 核心验证问题

Demo 第一版要验证：

- 用户能否看懂“命盘轴”和“现实发展路径”是分开的。
- 用户能否看懂命盘只提供底色和时间参照，不直接吞掉事件。
- 用户能否看懂执行、环境、关系、资源如何按时间展开。
- 用户输入的信息如何沉淀成结构化记忆，而不是只生成一段报告。
- 五轴之间的交叉引用是否直观。
- 一个事件同时影响多个轴时，是否能被清楚展示。

## 3. 必须展示的结构

### 3.1 五轴总览

展示一个人的五个主轴：

```text
命盘轴
执行轴
环境轴
关系轴
资源轴
```

每个轴只展示核心状态，不在总览页塞满细节。

### 3.2 命盘时间骨架

展示：

```text
L0 原始命盘
L1 终身底色
L2 当前大周期
L3 当前小周期
```

重点是让用户看到：

- L0/L1 是一次性详尽搭建。
- L2 只深挖当前大周期。
- L3 按当前问题展开。
- 命盘轴不记录现实事件。

### 3.3 执行路径

展示：

```text
L0 愿景
L1 大目标
L2 短期目标
L3 当下执行
```

重点是让用户看到：

- 愿景和大目标可能来自系统推测。
- 推测必须被含蓄印证。
- 当下执行要能反馈目标是否偏离。

### 3.4 环境变化

展示：

```text
时间颗粒度 × 环境方面
```

环境方面不能写死成几个固定字段。Demo 可以先用有限样例展示结构，但交互和文案上要表达它是开放分类。

### 3.5 关系网络

展示五类关系：

```text
血缘关系
亲密关系
核心朋友
商业关系
浅层关系
```

重点不是展示“关系好坏”，而是展示：

- 关系类型。
- 关系阶段。
- 关系结构。
- 关系事件。
- 这段关系如何影响执行、环境或资源。

### 3.6 资源变化

展示：

```text
时间颗粒度 × 资源方面
```

重点不是列能力清单，而是展示：

- 当前可调用资源。
- 正在增长的资源。
- 正在消耗的资源。
- 资源缺口。
- 可转化机会。

## 4. Demo 暂不做的事

第一版不做：

- 真实排盘引擎。
- 数据库。
- 登录注册。
- 后端 API。
- LLM 自动分析。
- 完整报告生成。
- 关系合盘。
- 付费。
- 社交匹配。
- 移动端适配的完整产品 UI。

第一版也不应该做成“算命展示页”。命盘只是五轴之一，不是页面唯一主角。

## 5. 推荐的第一版信息流

第一版 demo 可以先模拟一份静态人物档案。

信息流：

```text
打开 Person Dashboard
→ 看到五轴总览
→ 点击某一轴查看分层
→ 查看某个事件如何关联多个轴
→ 查看某条推测如何等待用户确认
→ 查看确认后如何变成稳定记忆
```

核心不是数据真实，而是结构真实。

## 6. 推荐的页面组成

如果后续开始实现 demo，建议从以下页面开始：

```text
1. Person Dashboard
2. Axis Detail
3. Memory Item Detail
4. Event Link View
5. Confirmation Flow
```

这些只是后续实现建议，本阶段不创建页面代码。

## 7. Demo 成功标准

第一版 demo 成功，不看功能复杂度，而看以下标准：

- 能一眼看懂五轴结构。
- 能看懂命盘和现实事件的边界。
- 能看懂事件如何沉淀为长期记忆。
- 能看懂事实、推测、假设、确认之间的区别。
- 能看懂关系和环境不是附属信息，而是理解人的主轴。
- 能看懂资源不是能力列表，而是可调用、消耗、缺口和转化条件。

## 8. 后续再展开的内容

只有在五轴结构被验证清楚后，再考虑：

- 真实排盘接入。
- 记忆写入交互。
- 用户输入解析。
- LLM 推理链。
- 数据库存储。
- 多人物关系网络。
- 真实报告和追问系统。

Demo 不应过早进入工程复杂度。第一阶段的价值是把体系讲清楚、看清楚、试清楚。
